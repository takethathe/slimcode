# slimcode GUI 右侧卡片区（json-render Card view）

Status: ready-for-agent

来源：ADR-0030（D1–D8）。经三轮 grill-with-docs 定型后由 to-spec 落盘。

## Problem Statement

GUI 目前只有 Transcript——assistant 消息与工具调用组成的一条水瀑。会话里最有价值的**状态**
（正在做什么、上一轮得出了什么、进度到哪）没有位置：它散落在消息里，读者要往回滚动、重读、
在脑子里自己重建。这类状态适合结构化呈现，而不是散文。

把这件事交给主 agent 也不对：模型要为此多花轮次、在 Message history 里留下痕迹，并开始决定
读者看到的布局——一个派生视图不该反过来改写对话。

## Solution

GUI 右侧新增 **Card view**：一个固定宽度、可折叠的面板，渲染 json-render 的 Spec。每轮**完成**
后，宿主自行启动一次性的 **Card generator**（独立线程、独立取消令牌、空工具集、不进 Message
history），让 provider 以 **SpecStream op**（一行一条 RFC 6902 JSON Patch）流式产出某一张卡的
内容。

op 行原样过线：webview 用 json-render 的编译器逐行 apply 并渐进渲染，宿主同时把同一行 apply 到
自己镜像的 Spec 上（唯一真相源），供下一轮生成、重连快照与淘汰使用。两端语义逐字对齐，因此流结束
后两份 Spec 必然相等。

## User Stories

1. 作为用户，我想每轮对话完成后右侧自动出现或更新一张卡，以便不用自己整理会话状态。
2. 作为用户，我想卡片是渐进长出来的（先出骨架，再一条条出现内容），以便看到它在工作，而不是
   静默几秒后整块出现。
3. 作为用户，我想卡片一开始生成就有可见的反馈（进度条、被清空的旧内容），以便知道请求已被受理。
4. 作为用户，我想任务看板这类卡片能跨多轮存活，以便它记录的是持续的状态而不是某一轮的快照。
5. 作为用户，我想持续更新的卡片不会被几张一次性的结果卡挤掉，以便我关心的看板不会莫名消失。
6. 作为用户，我想面板最多保留三张卡，以便它不会无限膨胀成第二个转录。
7. 作为用户，我想卡片按最近更新排序，以便最新的信息永远在最上面。
8. 作为用户，我想切换会话时卡片被清空，以便不会把上一个会话的结论误读成当前会话的。
9. 作为用户，我想新建会话时面板是空的，以便从零开始、不被残留内容干扰。
10. 作为用户，我想恢复历史会话时不会自动生成卡片，以便切会话不会悄悄产生费用。
11. 作为用户，我想随时手动触发一次生成，以便失败后重试或主动刷新。
12. 作为用户，我想在卡片生成中再点生成时得到明确反馈（已在生成），以便不会触发两份并发的请求。
13. 作为用户，我想我发出的下一条 prompt 会立刻取消进行中的卡片生成，以便不会看到一张基于旧状态
    的卡在我打字时慢慢浮现。
14. 作为用户，我想卡片生成失败时只在卡片区看到一个小的重试入口，以便对话本身不被无关错误打断。
15. 作为用户，我想坏的 op 行被丢弃、好的行继续生效，以便模型偶尔的格式失误不会让整张卡消失。
16. 作为用户，我想某个组件渲染失败时只影响那一块（占位降级），以便一张卡的结构错误不会炸掉面板。
17. 作为用户，我想折叠右侧面板，以便在需要更多宽度时给转录让出空间。
18. 作为用户，我想折叠卡片内部的次要内容或在卡片内切换视图，以便这些操作只在本地生效、不改动对话。
19. 作为用户，我想面板与转录各自独立滚动，以便阅读长卡片时不会把对话滚走。
20. 作为用户，我想卡片里的 Markdown 与转录里的渲染规则一致（标题、链接、代码），以便阅读体验统一。
21. 作为用户，我想卡片内容不进消息历史，以便它不会挤占上下文、也不会被模型当成对话的一部分。
22. 作为用户，我想卡片请求的 token 不计入 Usage HUD，以便我的用量数字仍然只描述真实对话。
23. 作为用户，我想在窗口变窄时布局不塌（面板可折叠、转录优先），以便小窗口下仍能用。
24. 作为用户，我想重启应用后卡片从空开始，以便我理解卡片的生命周期（它是一个视图，不是存档）。

## Implementation Decisions

**Card 的身份与容量**
- 固定 Card kind 词表：`task-board`（任务状态）、`result`（本轮结果）、`insight`（指标/进度一类）。
  模型只能对其中一个 kind 输出 op，不能发明新 kind。
- kind 即身份：重新生成同一 kind 即**替换**该卡（整卡重置后重建），而不是追加第四张。
- 单会话最多三张卡，按最近更新时间倒序排列；超出上限时淘汰最久未更新的一张。

**触发与并发**
- 触发点是宿主内部的 turn 结束事件：仅当 `stop_reason == Completed` 时自动生成；`cancelled` 与
  失败不触发（保留上一版卡片）。
- `new_session` / `resume_session` 不自动触发；手动生成是唯一的重试与刷新入口。
- 卡片生成单飞：进行中再次请求直接返回"已在生成"。
- 主 turn 开始时立即取消卡片生成（不 join，命令线程不阻塞在网络读上）；控制器销毁时 join 回收。
- 不新增生命周期状态：既有的"运行中"语义仍只表示主 turn 在跑。

**事件契约**
- 前端订阅一次，订阅命令返回当前全量快照，之后推四种扁平事件：
  - `card_begin { card_id }` —— 目标卡开始生成（前端清空该卡、显示进度条）
  - `card_op { card_id, op }` —— `op` 是**单行 JSON 字符串**，原样透传，不解构成对象
  - `card_end { card_id, ok }` —— 结束，`ok` 表示是否至少有一行成功应用
  - `cards_snapshot { cards }` —— 全量对齐（订阅返回、会话切换、手动刷新）
- 事件顺序保证"先 begin、若干 op、后 end"，同一卡的 op 之间保持发送顺序。

**双端 apply 与切行**
- 前端每张卡持有一个 SpecStream 编译器实例，`card_op` 时把 `op + "\n"` 推入，用返回的结果作为
  渲染输入；`card_end` 时 flush 残行。
- 宿主侧实现同语义的容忍 applier：`replace` 目标不存在也写入、`add` 自动创建父路径、`remove`
  缺路径静默，支持 `move` / `copy` / `test`。**不使用严格的 RFC 6902 实现**——风险不是合规，而是
  "前端接受、宿主拒绝"造成真相与画面分叉。
- 两端都以 `\n` 切行并保留不完整残行（provider 的文本碎片会把一行劈开）。
- 宿主**先转发再应用**：任何宿主侧意外都不能吞掉一行前端本可渲染的 op。

**渐进渲染**
- 生成提示要求：先 `/root`、一个元素一条 op、单条 `Text` 载荷不超过约 120 字符，禁止把整张卡
  塞进一条 op 的 `value`（否则界面会静默数秒后整块出现）。
- 前端按动画帧合批：一帧内到达的多条 op 只触发一次渲染。
- 不做逐字打字机效果（对同一 `Text` 反复 `replace` 内容）：op 与 token 成本成倍上升，且会把模型
  带偏成"只改文本不改结构"。

**组件目录**
- 手写 9 个 catalog 组件 + 1 个未知类型占位，沿用 GUI 现有浅色 slate/indigo 设计语言，不引入
  json-render 的 shadcn 组件包（Radix + 另一套视觉，对一个只读面板是负担）。
- 组件：`Card`（标题 + 子节点）、`Stack`（方向/间距）、`Text`（内容 + 视觉权重）、`List`
  （条目 + 可选完成态）、`KeyValue`（标签/值）、`Badge`（文本 + 色调）、`Progress`（0–100）、
  `Divider`、`Markdown`（复用 GUI 已有的 Markdown 渲染规则与链接外开行为），以及 `Fallback`。
- 只允许纯前端动作（折叠、切换、局部状态）；卡片不得产生能回到宿主的副作用。

**提示词的数据边界**
- 系统提示（组件词表、op 格式、粒度约束）由前端在运行时用 catalog 生成并随请求透传：单一描述，
  无构建期代码生成，因而没有需要防漂移的第二份事实。
- user 提示由宿主拼装：最近约 20 条消息的紧凑投影（用户/助手保留全文，工具调用只留名称，工具
  结果截断到约 400 字符，更早的消息整体省略并注明）、现有卡片的 `currentSpec`、本次触发原因。

**provider 调用**
- 直接以两条消息调用 provider：系统提示 + user 提示；工具列表为空。
- 配置沿用会话的解析结果（`gui.toml` 覆盖 > 环境 > `config.toml` > 默认），不引入第二套模型配置。
- 设保守的响应上限（4000 tokens）。
- 不使用 AgentSession：没有工具循环、不写 Message history、不发 SDK 事件。
- 其 token 用量**不计入**会话累计、Usage HUD 与上下文百分比——那些数字回答"这次对话花了多少"，
  一个展示用旁路请求会污染答案。该成本只落日志。

**失败语义**
- 逐行解析：坏行丢弃、好行保留。
- 一条 op 都没成功：保留上一版卡片，并在面板内给出重试入口；不进 Transcript，也不进全局错误横幅。
- 单张卡结构错误：由渲染器逐元素错误边界与 `Fallback` 占位降级，不影响其他卡。

**持久化**
- 卡片只存在于宿主内存；切换会话清空；重启丢失。与"会话累计用量不持久化"的既有取向一致；
  因为宿主持有唯一真相，落盘是后续可增量添加的能力。

**依赖**
- json-render 的 core 与 react 渲染器固定 0.21.3（与本地参考仓库同版本），以及其 zod 4 peer 依赖，
  从包管理器安装；本地 clone 仅作源码参考，不作为构建输入。

## Testing Decisions

**好测试的标准**
- 只断言外部行为：宿主侧断言"收到哪些事件、顺序如何、快照内容如何"，不断言内部字段或私有方法；
  前端断言"给定一串 op，最终渲染出什么"，不关心编译器内部结构。
- 跨语言一致性用**共享 fixture** 表达：一份 op 流文本 + 期望的最终 Spec JSON，Rust 与 TS 两侧测试
  各自读它并断言，而不互相调用。

**测试 seam（优先复用既有 seam）**
- **Rust 主 seam：控制器**。它已经是纯 Rust 的测试面（provider 工厂与工具集可在测试中注入，事件
  通过 sink 记录）。卡片功能沿用同一套注入：脚本化的假 provider 产出 op 行文本碎片，记录型 sink
  收集卡片事件。生成器、单飞、取消、触发条件、淘汰、快照都在这一层验证。
- **Rust 从属 seam：容忍 applier 的纯函数**。表驱动覆盖六个 op 与三个容忍边界；由控制器测试间接
  覆盖端到端行为。
- **TS 主 seam：卡片归约的纯函数**（op 行/事件 → 每张卡的 Spec 与面板状态）。残行、坏行、多卡
  分组、帧合并都在这一层验证。
- **TS DOM seam：卡片面板组件**，只测渲染结果、占位降级、空态、进度条与折叠。

**模块与先例**
- 宿主侧：控制器测试的先例（假 provider 的脚本化 delta 批次、事件 kind 断言、等待状态收敛）已存在
  且可直接沿用；applier 的表驱动风格与既有的 wire 映射穷尽性测试同源。
- 前端侧：既有转录归约的纯函数单测（Vitest）与 Markdown 渲染的 DOM 单测（testing-library + jsdom）
  分别是这两个 seam 的先例。
- 运行时：GUI 改动需在开发模式下用既有 devshot 协议对真实 webview 截图确认（见开发文档的 GUI 一节）。

## Out of Scope

- 卡片持久化、跨 resume 恢复、写入会话日志或任何共享存储。
- 卡片动作回到宿主（点击重跑工具、把卡片内容发成新 prompt）。
- 用户自定义 catalog、卡片类型可配置、卡片内表单或输入控件。
- 卡片请求的用量计量与展示。
- TUI / CLI 侧的卡片呈现。
- 逐字流式文本（按 token 逐步改写同一段文本）。
- 多窗口、托盘、全局快捷键等宿主层扩展。

## Further Notes

- 术语按 GLOSSARY：**Card view** / **Card** / **Card generator** / **SpecStream op**。"json render
  agent" 这个说法已废弃——它会与 `AgentSession`（带工具循环的 turn loop）撞词。
- 全部取舍与拒绝的备选记录在 ADR-0030，本规格是其可执行的展开。
- 两条有意接受的边界：卡片在会话切换与重启后丢失；卡片生成的 token 成本在 UI 上不可见。
- 实施按仓库改动流程推进（需求 → 计划 → 测试先行 → 全绿 → 文档 → review → 提交），门禁在 GUI
  项目自己的范围内跑，不触碰工作区 crate 的依赖矩阵。
