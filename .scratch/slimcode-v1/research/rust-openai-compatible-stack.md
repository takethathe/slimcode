# Research: Rust stack for an OpenAI-compatible chat provider (SSE streaming + tool_calls) — targeted at Bailian

Scope: evaluate `async-openai` (custom base_url, SSE, tool calls, usage, feature gates) vs a hand-rolled `reqwest` + SSE approach (`reqwest-eventsource` vs `eventsource-stream` vs manual `bytes_stream`), then recommend a slim `Provider` trait optimized for an OpenAI-compatible Bailian backend. All claims cite primary docs.rs / crates.io / source URLs. Version studied: **async-openai 0.41.3**, **reqwest-eventsource 0.6.0**, **eventsource-stream 0.2.3**.

## Summary

`async-openai` fully supports all four requirements (custom `base_url`, SSE streaming, `tool_calls` in requests and responses, `usage`/token counts), but is a heavy dependency (reqwest 0.13 + eventsource-stream + tower + tokio-stream + derive_builder + macros, all gated behind an internal `_api` feature). For a **slim** provider targeting an OpenAI-compatible Bailian backend, the recommended path is a thin hand-rolled client: `reqwest` (rustls, `json` + `stream` features) + `eventsource-stream` 0.2.3 (transport-agnostic SSE framing — the same crate async-openai itself uses internally) + `serde`/`serde_json`, with a small `ProviderEvent`/`ToolCallDelta` accumulation layer. `reqwest-eventsource` is a viable alternative only if you accept its reqwest 0.12 pin and want built-in auto-retry, which is undesirable for interrupted chat streams.

## Findings

### Q1. async-openai: capabilities, feature gates

1. **Custom base_url: YES.** `OpenAIConfig::with_api_base(...)` overrides the default `OPENAI_API_BASE = "https://api.openai.com/v1"`; `OPENAI_BASE_URL` env var also works, and `with_header(...)` injects per-request headers (custom headers take precedence). The `Config` trait builds URLs as `format!("{}{}", api_base, path)`, so any OpenAI-compatible host works by setting `api_base` (e.g. Bailian's `https://dashscope.aliyuncs.com/compatible-mode/v1`). Source: [OpenAIConfig docs](https://docs.rs/async-openai/latest/async_openai/config/struct.OpenAIConfig.html), [config.rs source](https://docs.rs/async-openai/latest/src/async_openai/config.rs.html). Note: `OpenAIConfig` is gated "Available on crate feature `_api` only".
2. **SSE streaming: YES.** `Chat::create_stream(&CreateChatCompletionRequest) -> Result<ChatCompletionResponseStream>` POSTs `/chat/completions`, forces `stream = true`, and returns `ChatCompletionResponseStream = StreamResponse<CreateChatCompletionStreamResponse>`, described as "Parsed server side events stream until a `[DONE]` is received from server." Source: [chat.rs source](https://docs.rs/async-openai/latest/src/async_openai/chat.rs.html), [ChatCompletionResponseStream type alias](https://docs.rs/async-openai/latest/async_openai/types/chat/type.ChatCompletionResponseStream.html).
3. **Streaming chunk model:** `CreateChatCompletionStreamResponse { id, choices: Vec<ChatChoiceStream>, created, model, service_tier, system_fingerprint, object, usage: Option<CompletionUsage> }`; each `ChatChoiceStream { index, delta: ChatCompletionStreamResponseDelta, finish_reason: Option<FinishReason>, logprobs }`. Source: [CreateChatCompletionStreamResponse](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.CreateChatCompletionStreamResponse.html), [ChatChoiceStream](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.ChatChoiceStream.html).
4. **tool_calls in requests: YES.** `CreateChatCompletionRequest` includes `tools: Option<Vec<ChatCompletionTools>>`, `tool_choice: Option<ChatCompletionToolChoiceOption>`, `parallel_tool_calls: Option<bool>`, plus legacy `functions`/`function_call`, `stream: Option<bool>`, and `stream_options: Option<ChatCompletionStreamOptions>`. `ChatCompletionTool { function: FunctionObject }`. Note: the streaming **request** is the same `CreateChatCompletionRequest` (the task's listed `ChatCompletionRequestStream` URL returns HTTP 404 — that type no longer exists in 0.41.3; `create_stream` reuses the same request struct). Source: [CreateChatCompletionRequest](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.CreateChatCompletionRequest.html), [ChatCompletionTool](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.ChatCompletionTool.html).
5. **tool_calls in responses: YES.** Non-stream: `ChatCompletionMessageToolCall { id, function: FunctionCall }`. Stream: `ChatCompletionMessageToolCallChunk { index: u32, id: Option<String>, type: Option<FunctionType>, function: Option<FunctionCallStream> }`, where `FunctionCallStream { name: Option<String>, arguments: Option<String> }` — `arguments` arrive as JSON **fragments** across many deltas that must be accumulated by `index` and parsed as JSON only at the end (docs explicitly warn the model "does not always generate valid JSON … Validate the arguments"). Source: [ChatCompletionMessageToolCallChunk](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.ChatCompletionMessageToolCallChunk.html), [FunctionCallStream](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.FunctionCallStream.html), [ChatCompletionMessageToolCall](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.ChatCompletionMessageToolCall.html). The delta is exposed via `ChatCompletionStreamResponseDelta { content, function_call (deprecated), tool_calls, role, refusal }`. Source: [ChatCompletionStreamResponseDelta](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.ChatCompletionStreamResponseDelta.html).
6. **usage/token counts: YES.** `CompletionUsage { prompt_tokens, completion_tokens, total_tokens, prompt_tokens_details, completion_tokens_details }`. Non-stream: `CreateChatCompletionResponse.usage: Option<CompletionUsage>`. Stream: `usage` appears only on the final chunk **if** you set `stream_options: { "include_usage": true }` (`ChatCompletionStreamOptions { include_usage, include_obfuscation }`), and the docs warn "If the stream is interrupted, you may not receive the final usage chunk." Source: [CompletionUsage](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.CompletionUsage.html), [CreateChatCompletionResponse](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.CreateChatCompletionResponse.html), [ChatCompletionStreamOptions](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.ChatCompletionStreamOptions.html).
7. **Config-gated / unstable features (0.41.3):** `default = ["rustls"]` (reqwest/rustls with rustls-platform-verifier). There is **no `unstable` feature in 0.41.3** (that existed only in older releases). The relevant gates: API wrapper = `chat-completion = ["chat-completion-types", "_api"]`; types-only = `chat-completion-types`; `_api` is an **internal** feature ("Internal feature to enable API dependencies") that pulls reqwest 0.13, eventsource-stream 0.2, tokio-stream, tokio-util, tower, secrecy, async-openai-macros, etc.; `byot` = "bring your own types" (async-openai-macros rewrites `Chat::create`/`create_stream` into generic `T0: Serialize`, `R: DeserializeOwned` signatures with `R: MaybeSend + 'static` for streams); `full` enables all features; `types` enables all type features. Source: [Cargo.toml.orig](https://docs.rs/crate/async-openai/latest/source/Cargo.toml.orig), [features page](https://docs.rs/crate/async-openai/latest/features), [chat.rs byot attributes](https://docs.rs/async-openai/latest/src/async_openai/chat.rs.html).
8. **Crate health:** async-openai 0.41.3, ~7.64M total downloads, ~2.4M recent, MIT, actively updated. Source: [crates.io API](https://crates.io/api/v1/crates/async-openai).

### Q2. Hand-rolled reqwest + SSE parsing: reqwest-eventsource vs eventsource-stream vs manual bytes_stream

9. **reqwest-eventsource 0.6.0** — "Provides a simple wrapper for reqwest to provide an Event Source implementation … uses eventsource_stream to wrap the underlying Bytes stream, and retries failed requests." `RequestBuilderExt::eventsource()` → `EventSource`; yields `Event::Open | Event::Message(MessageEvent)`; configurable retry policies (`Constant`, `ExponentialBackoff`, `Never`, `DEFAULT_RETRY`); rich `Error` enum (`Utf8`, `Parser`, `Transport`, `InvalidContentType`, `InvalidStatusCode`, `InvalidLastEventId`, `StreamEnded`). Health: ~10.6M total / ~2.5M recent downloads, last published 2024-03-29, MIT/Apache-2.0. **Watch-outs:** pins `reqwest ^0.12.0` (async-openai 0.41.3 is on reqwest 0.13 → version skew if combined) and its automatic retry-on-error is the wrong default for chat streaming (you do not want silent reconnects mid-generation or after `[DONE]`; you can set `retry` to `Never`). Source: [reqwest_eventsource docs](https://docs.rs/reqwest-eventsource/latest/reqwest_eventsource/), [EventSource](https://docs.rs/reqwest-eventsource/latest/reqwest_eventsource/struct.EventSource.html), [Error](https://docs.rs/reqwest-eventsource/latest/reqwest_eventsource/enum.Error.html), [retry module](https://docs.rs/reqwest-eventsource/latest/reqwest_eventsource/retry/index.html), [dependencies JSON](https://crates.io/api/v1/crates/reqwest-eventsource/0.6.0/dependencies), [crates.io API](https://crates.io/api/v1/crates/reqwest-eventsource).
10. **eventsource-stream 0.2.3** — transport-agnostic SSE framing on any `Stream<Item = Result<Bytes, E>>`: `reqwest::Client::new().get(...).send().await?.bytes_stream().eventsource()`. Yields `Event { event, data, id, retry }`; errors `EventStreamError { Utf8, Parser, Transport }`. Dependencies are tiny and runtime-free (`futures-core`, `nom`, `pin-project-lite`); ~770 code lines per crates.io linecounts. Health: ~20.0M total / ~7.9M recent downloads, last published 2022-02-17 (stable but dormant), MIT/Apache-2.0. **Watch-outs:** no retry/reconnect logic — you own reconnection and `[DONE]` handling, but that's actually what you want for chat. Source: [eventsource_stream docs](https://docs.rs/eventsource-stream/latest/eventsource_stream/), [Event](https://docs.rs/eventsource-stream/latest/eventsource_stream/struct.Event.html), [EventStreamError](https://docs.rs/eventsource-stream/latest/eventsource_stream/enum.EventStreamError.html), [dependencies JSON](https://crates.io/api/v1/crates/eventsource-stream/0.2.3/dependencies), [crates.io API](https://crates.io/api/v1/crates/eventsource-stream). It is the crate async-openai itself uses internally (async-openai 0.41.3 depends on `eventsource-stream = "0.2"`) — Source: [Cargo.toml.orig](https://docs.rs/crate/async-openai/latest/source/Cargo.toml.orig).
11. **Manual `bytes_stream` parsing** — full control (custom framing, keep-alive comments, CR/LF handling, multi-line `data:` accumulation), but you re-implement the SSE line protocol and must handle chunk boundaries splitting mid-line and mid-JSON, the `[DONE]` terminator, and Bailian-specific heartbeats. Low dependency cost, moderate effort (~150–250 lines), and the highest risk of subtle framing bugs; not recommended when a mature parser (eventsource-stream, ~770 code lines) already exists. Source for parser size: [crates.io API](https://crates.io/api/v1/crates/eventsource-stream).
12. **Effort/risk of parsing streaming tool_call deltas (independent of SSE crate choice):** the hard part is not SSE framing — it's delta accumulation. Each tool call arrives as `ChatCompletionMessageToolCallChunk` identified by `index`; `id` and `name` typically appear on the first fragment and `arguments` are streamed as partial JSON fragments over many chunks; you must buffer per-`index`, concatenate `arguments`, then `serde_json::from_str` at `finish_reason == tool_calls`; the model may emit non-JSON arguments, so validation is mandatory. This is the same accumulation logic whether you use async-openai's parsed stream, eventsource-stream, or a manual parser — async-openai saves you only the transport/framing, not the accumulation. Source: [FunctionCallStream](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.FunctionCallStream.html), [ChatChoiceStream.finish_reason](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.ChatChoiceStream.html).

### Q3. HTTP client / JSON / SSE selection

13. **HTTP client: reqwest with rustls.** async-openai's default is `default = ["rustls"]` → `reqwest/rustls` (rustls-platform-verifier roots); it also offers `native-tls`, `native-tls-vendored`, `rustls-no-provider`. For a slim hand-rolled client use `reqwest = { version = "0.13", default-features = false, features = ["json", "stream", "rustls-tls"] }` (or `"rustls"` to match async-openai). If you instead adopt `reqwest-eventsource`, its reqwest is `^0.12.0` (older) — a real version-skew consideration. Sources: [Cargo.toml.orig](https://docs.rs/crate/async-openai/latest/source/Cargo.toml.orig), [reqwest-eventsource deps](https://crates.io/api/v1/crates/reqwest-eventsource/0.6.0/dependencies).
14. **JSON: serde + serde_json.** Used by async-openai for all types and by any hand-rolled client; both SSE crates are serde-adjacent. Optionally `derive_builder` for fluent request builders (async-openai uses it via `chat-completion-types`). Sources: [Cargo.toml.orig](https://docs.rs/crate/async-openai/latest/source/Cargo.toml.orig), [CreateChatCompletionRequest](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.CreateChatCompletionRequest.html).
15. **SSE crate: prefer `eventsource-stream` 0.2.3** as the standalone framing layer (transport-agnostic, tiny, and the proven parser async-openai relies on); pick `reqwest-eventsource` only if you want its auto-retry + status-code/content-type validation and accept the reqwest 0.12 pin. Sources: [eventsource-stream docs](https://docs.rs/eventsource-stream/latest/eventsource_stream/), [reqwest_eventsource docs](https://docs.rs/reqwest-eventsource/latest/reqwest_eventsource/).

### Q4. Recommendation: slim Provider trait for an OpenAI-compatible Bailian backend

16. **Chosen stack:** `reqwest 0.13` (default-features=false, `json` + `stream` + `rustls`) + `eventsource-stream 0.2.3` + `serde`/`serde_json` + `futures-core`/`tokio`. Rationale: it is the exact primitives async-openai composes (reqwest + eventsource-stream) minus the heavy optional deps (`tower`, `tokio-stream`, `tokio-util`, `secrecy`, `derive_builder`, `async-openai-macros`), with no internal `_api` feature gate and no risk that Bailian's slightly-different JSON breaks strict generated types. Sources: [Cargo.toml.orig](https://docs.rs/crate/async-openai/latest/source/Cargo.toml.orig), [eventsource_stream example](https://docs.rs/eventsource-stream/latest/eventsource_stream/).
17. **Keep async-openai as the fallback path.** If full OpenAI-fidelity types and a pre-parsed SSE stream are more valuable than slimness, `OpenAIConfig::with_api_base(bailian_url)` + `Client::with_config` + `chat().create_stream(...)` with `features = ["chat-completion"]` delivers everything in Q1 with ~20 lines. It works for any host because `url(path) = api_base + path` and the endpoint is exactly `/chat/completions`. Source: [OpenAIConfig](https://docs.rs/async-openai/latest/async_openai/config/struct.OpenAIConfig.html), [config.rs source](https://docs.rs/async-openai/latest/src/async_openai/config.rs.html), [chat.rs source](https://docs.rs/async-openai/latest/src/async_openai/chat.rs.html).
18. **Recommended Provider trait shape** (slim, no async-openai types leaked):
    ```rust
    use futures_core::Stream;

    pub enum ProviderEvent {
        TextDelta(String),
        ToolCallDelta { index: u32, id: Option<String>, name: Option<String>, arguments_fragment: String },
        Finish { reason: FinishReason },
        Usage(Usage),   // only if stream_options.include_usage=true
    }

    pub trait ChatProvider: Send + Sync {
        /// Non-streaming completion (short responses / when streaming is disabled).
        fn complete(&self, req: ChatRequest) -> impl std::future::Future<Output = Result<ChatResponse, ProviderError>> + Send;
        /// SSE streaming completion; caller accumulates tool_call deltas by index.
        fn stream(&self, req: ChatRequest) -> impl Stream<Item = Result<ProviderEvent, ProviderError>> + Send;
    }
    ```
    Internally `stream()` = POST `/chat/completions` with `stream: true` + `stream_options.include_usage: true`, then `bytes_stream().eventsource()`, and per `data` (skip `[DONE]` and comments) `serde_json::from_str::<StreamChunk>`; map `delta.content` → `TextDelta`, `delta.tool_calls` → `ToolCallDelta`, `choice.finish_reason` → `Finish`, chunk `usage` → `Usage`. Tool-call accumulation (concatenate `arguments` per `index`, JSON-parse at `Finish(tool_calls)`) lives in the caller or an `Agent` layer, mirroring the semantics documented on [ChatCompletionMessageToolCallChunk](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.ChatCompletionMessageToolCallChunk.html) / [FunctionCallStream](https://docs.rs/async-openai/latest/async_openai/types/chat/struct.FunctionCallStream.html).
19. **Bailian specifics to verify at integration time (not covered by docs.rs):** exact compatible-mode endpoint (`/compatible-mode/v1/chat/completions`), auth scheme (async-openai always sends `Authorization: Bearer <key>` via `Config::headers`, and extra headers can be layered via `with_header`), whether Bailian honors `stream_options.include_usage` (older compatible-mode endpoints sometimes omit the final usage chunk), and whether it emits a terminating `[DONE]`. Source for header behavior: [config.rs source](https://docs.rs/async-openai/latest/src/async_openai/config.rs.html).

## Gaps

- **Bailian wire behavior is not verifiable from docs.rs/crates.io:** exact compatible-mode base path, auth header semantics, support for `stream_options.include_usage`, and `[DONE]` emission must be confirmed against the actual Bailian (DashScope compatible-mode) endpoint with a live request, or its vendor docs.
- **Strictness of async-openai's generated types vs Bailian JSON:** unknown whether Bailian returns extra/omitted fields that fail serde deserialization on async-openai's derived structs; only live testing decides whether the async-openai fallback path needs `byot` custom types.
- **reqwest-eventsource's reqwest 0.12 pin** would force a second reqwest major version into the dependency tree if combined with reqwest 0.13 code; acceptable standalone but a maintenance smell.
- Suggested next step: run a tiny spike against Bailian compatible-mode with `curl` + `eventsource-stream` to confirm framing (keep-alive, final usage chunk, `[DONE]`) before committing to the Provider trait design.
