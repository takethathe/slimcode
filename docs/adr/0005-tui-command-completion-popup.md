# TUI `/` completion popup: fuzzy matcher in slimcode-commands, candidate assembly in slimcode-common, popup UI in the TUI

> Superseded in part by [ADR-0007](./0007-tui-r2-alignment-with-pi.md) D3/D4: the popup now renders as bare SelectList rows (no bordered box / ` completion ` title) and sits **above** the input box instead of below it, so the input box stays position-stable when the popup opens/closes. The matching, candidate assembly, and key state machine described here are unchanged.
>
> **Revision (prediction refinement)**: two follow-up refinements change the *matching* and *selection* semantics described below, keeping everything else. (1) Skills are scored on their **bare name** only — the `/skill:` trigger prefix is never part of the matched text (its `s`/`k`/`i`/`l` letters would otherwise match every skill and drown the name's own boundary bonuses); a typed `/skill:name` trigger is likewise stripped to its name part before matching, and `/skill:` alone lists all skills like a bare `/`. Candidate *values* stay canonical `/skill:name`. (2) The popup's pre-selected row **tracks the re-ranked best match on every keystroke** while the user only types; the selection becomes sticky (kept by value while still a candidate) only after the user moves it with `↑`/`↓`/`PgUp`/`PgDn` during the current popup, and a manual pick that gets filtered out falls back to auto.

The TUI gets a live completion popup for `/` input: typing `/` at the start of the input box opens a fuzzy candidate list (commands + installed skills) below the input box; `↑`/`↓` move the selection, `Tab` commits the selected spelling to the buffer with a trailing space (cursor after it, no submit), `Enter` expands the selection and submits it, `Esc` cancels. The design is modelled on pi's editor/provider split, but kept dependency-light: the general fuzzy subsequence matcher lives in `slimcode-commands` (a leaf crate, pure data + pure functions, so it is trivially unit-testable), the merged command+skill candidate assembly lives in `slimcode-common::skills` (which already couples the `COMMANDS` registry with the skill list), and only the popup rendering + key state machine live in the TUI.

**Considered Options**: putting the fuzzy matcher in `slimcode-common` instead (rejected — it has no dependency on commands and would force a reverse dependency or duplicate logic), and putting the whole popup in the TUI (rejected — the ranking logic would become untestable without a terminal and would duplicate the existing `suggest`/`combined_suggestions` matching).

**Consequences**: command names are matched fuzzy (subsequence scoring: consecutive runs, word boundaries and exact matches rewarded; gaps and late positions penalised — integer-scaled from pi's `fuzzy.ts`), whereas the existing `suggest`/`combined_suggestions` stay prefix-only for the post-submit "did you mean" path, so the two matching behaviours coexist intentionally. Completion values are command bare spellings (`/usage`, `/resume`) or the canonical skill trigger `/skill:name`, never usage strings with argument placeholders, so a committed candidate always resolves through `find`/`find_skill` when submitted. The candidate pool is fed from the TUI app's skills snapshot, which is refreshed after a runtime `/install-skill` — newly installed skills show up in the popup and `did you mean` immediately, without restarting the TUI.
